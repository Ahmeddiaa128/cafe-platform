# Café Platform: an evolving AWS architecture, built with Terraform and Ansible

A hands-on DevOps project that takes a small business website (a café) from a
static page on S3 to a highly available, auto-scaling, secured, three-tier web
application with scheduled serverless reporting, built **incrementally in six
versions**. Each version solves one business requirement and changes one
architectural concern, so every step is small enough to understand, test and roll back.

Infrastructure is defined as code with **Terraform** (reusable modules, separate
`dev` and `prod` environments), servers are configured with **Ansible** (roles,
tags, idempotent tasks), and secrets live in **SSM Parameter Store**, never in the repository.

> Built and tested in an AWS Academy sandbox (us-east-1). Its restrictions (explicit
> denies, a service control policy, no Multi-AZ RDS, a restricted IAM role) shaped several
> design decisions. They are documented honestly below rather than hidden.

## The six versions

| Version | Business requirement | What was built | How |
|---|---|---|---|
| **V1** | Static website for a small business | S3 static website hosting with a public-read bucket policy | AWS Console |
| **V2** | Dynamic content and online ordering | Apache, PHP and MariaDB on one EC2 instance, configuration in SSM Parameter Store | Terraform + manual deployment |
| **V3** | Reduce database maintenance and secure its data | Database moved to Amazon RDS (MariaDB) in private subnets, deployment automated | Terraform + Ansible |
| **V4** | Enhance the security of the web application | Custom NACLs per subnet tier, least-privilege security group egress | Terraform |
| **V5** | Handle more traffic and survive failures | ALB, Auto Scaling group over two AZs, custom AMI | Terraform + AMI pipeline |
| **V6** | Reporting with less operational burden and lower cost | Scheduled serverless sales report: EventBridge, two Lambda functions, SNS email | AWS Console |

## Key design decisions

**Modules, not copies.** One module per concept (network, database, ALB...). Environments
differ only in the values they pass in, such as CIDR ranges and NAT settings. When a
requirement changes, a module gains a variable instead of being duplicated per version.

**State lives in the data tier.** Web servers are stateless and replaceable. The schema and
orders live in RDS. The database initialisation script drops and recreates the database,
so it is **never** run automatically at boot: running it from every new Auto Scaling
instance would wipe customer orders. It is a deliberate, idempotent Ansible step run once.

**Secrets never touch Git.** Terraform generates the database password with
`random_password`, stores it as a SecureString, and the application and Ansible read it at run
time. The password is generated in the root module and passed to both consumers, which
breaks a dependency cycle between the database and the parameter module.

**Defense in depth.** Security groups (stateful, per instance) and NACLs (stateless, per
subnet) filter independently. The database accepts port 3306 only from the web tier, has
no public access, and its security group has no egress rules at all. Web server egress
is limited to HTTPS, HTTP for package repositories, and MySQL to the database group.

**Golden AMI for the Auto Scaling group.** Instances must come up ready without anyone
logging in. A builder instance is configured with Ansible (`--tags web,app`), captured as an
AMI, and the Auto Scaling group launches from it. The AMI contains no secrets.

**Environment chosen explicitly.** `ansible.cfg` has no default inventory, so a command
cannot accidentally run against the wrong environment: `-i inventories/<env>/hosts.ini`
is always required.

## What I learned

**Terraform**
- Structuring reusable modules and passing outputs between them.
- Reading dependency graphs: diagnosing a `Cycle` error and breaking it by moving a shared value to the root.
- Provider and module version constraints: a community module required a newer AWS provider than I had pinned.
- Why security group egress rules are separate resources, and how leaving inline `egress` blocks out removes AWS's default allow-all.
- What `-target` is for, and why it should not be a routine workflow.

**AWS networking and security**
- Stateful (security group) versus stateless (NACL) filtering, and why NACLs need ephemeral port ranges for replies.
- What link-local services (DNS, metadata, NTP) are not filtered by either layer.
- Why a Lambda function inside a VPC has no internet without NAT or endpoints, and how splitting a pipeline into two functions avoids paying for either.
- Why S3 is a regional service outside any VPC.
- Why WAF attaches to an ALB or CloudFront and not to EC2.

**High availability**
- How Auto Scaling health checks interact with a load balancer: with `ELB` checks, an unhealthy target gets replaced in a loop until the image is fixed.
- Testing an AMI before pointing a scaling group at it.
- The difference between Multi-AZ (availability, standby) and read replicas (read scaling).

**Ansible**
- Roles, handlers, tags, and templates; idempotency, checking state before running a destructive step.
- Lookups against SSM so credentials stay out of inventories.

**Working in a restricted environment**
- Reading an `explicit deny` message, identifying whether it comes from an identity policy or a service control policy, and designing around it.
- Testing a service with the CLI before writing code for it.
- Documenting a limitation clearly instead of pretending it does not exist.

## Problems solved along the way

| Problem | Diagnosis | Fix |
|---|---|---|
| Terraform cannot create the S3 bucket | Sandbox denies `s3:GetBucketObjectLockConfiguration`, which the provider reads after creation | V1 built in the Console; module kept as reference |
| Provider version conflict | The VPC module needs a newer AWS provider than the pin | Aligned the provider constraint |
| `Cycle` between database and SSM module | Each needed the other's output | Password generated in the root module |
| SSH timeouts | Administrator's public IP changed | Updated one variable feeding both security group and NACL |
| Application used Secrets Manager (unavailable) | Not in the allowed service list | Rewrote the PHP client to use SSM Parameter Store |
| Auto Scaling loop killing instances | `ELB` health check failing | Inspected instances from inside, found the AMI lacked the web server, rebuilt and verified it |
| `StartInstanceRefresh` denied | Service control policy | Replaced instances by terminating them so the group rebuilt from the new template |

## Getting started

Prerequisites: Terraform ≥ 1.5, AWS CLI, Ansible, Git, and AWS credentials for
us-east-1 (the sandbox's temporary credentials work).

```bash
git clone https://github.com/Ahmeddiaa128/cafe-platform.git
cd cafe-platform/terraform/environments/prod
```

1. Create `terraform.tfvars` (git-ignored):

   ```hcl
   ssh_allowed_cidrs = ["YOUR_PUBLIC_IP/32"]
   ```

2. Deploy the infrastructure:

   ```bash
   terraform init
   terraform plan
   terraform apply
   ```

3. Configure the servers and load the schema:

   ```bash
   cd ../../../ansible
   # set ansible_host in inventories/prod/hosts.ini
   ansible -i inventories/prod/hosts.ini web -m ping
   ansible-playbook -i inventories/prod/hosts.ini playbooks/site.yml --tags web,app
   ansible-playbook -i inventories/prod/hosts.ini playbooks/site.yml --tags db   # once only
   ```

4. For the V5 setup, capture an AMI from the configured builder (tag
   `Project=cafe-platform`), then enable the `alb` and `asg` modules.
5. Always run `terraform destroy` when finished; the load balancer and database are billed hourly.

Tag selection: `--tags web,app` configures the server and the application; `--tags db`
initialises the schema and is deliberately separate.

## Honest limitations

- **V1 and V6 were built in the AWS Console**, not Terraform, because of sandbox
  restrictions (V1) and the serverless reporting pipeline being built separately from
  the Terraform stack (V6). The V6 write-up describes the Terraform resources that would
  represent it.
- **RDS is single-AZ.** The sandbox does not support Multi-AZ. The subnet group already spans two
  AZs, so enabling `multi_az` in a regular account is a one-line change.
- **Instances are in public subnets**, because there is no NAT Gateway in this
  budget-limited environment. A production design would use private subnets and NAT or VPC endpoints.
- **HTTP only.** HTTPS needs a certificate and a domain (domain registration is not available in the sandbox).
- **Terraform state is local** and contains generated secrets (git-ignored). A production
  setup would use an encrypted remote backend.
- **SSM parameter paths are not environment-scoped**, so dev and prod cannot coexist in one account.
- **Updating the application means building a new AMI.** A pipeline (for example Packer) would automate it.
- **VPC Flow Logs** were attempted but the sandbox role cannot be used by the Flow Logs service.
